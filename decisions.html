Crossroads

Choices with meaningful rewrite, ownership, security, or product cost if they are wrong.

C1

Runtime and scope boundary

Accepted

Which VS Code hosts and Markdown document types belong in the first complete product?

Impact if wrong

Adding browser-hosted VS Code later changes bundling and file access; accepting arbitrary Markdown later replaces the two typed document models with a generic rendering product.

Proposed choice

Build a local desktop VS Code extension for GH-*.md issue records and PP-*.md Planpoints only. Keep VS Code for the Web, generic Markdown, roadmap, issue-plan, and review documents out of scope.

Desktop and two schemas Delivers the requested flow with a small, explicit compatibility contract. Recommended
Desktop and web hosts Broadens access now but requires dual-host packaging and virtual-workspace behavior.
Generic Markdown Previews more files but cannot guarantee the exact document-specific design.
Reasoning and review consequence

Why

The IDEA explicitly names VS Code and exactly two document templates. A focused desktop extension is the smallest coherent product and avoids speculative compatibility.

Review consequence

Prototype and manual verification will cover both supported filename patterns in desktop VS Code. Other Markdown files must fail with a clear unsupported-document message.

C2

Canonical source and generated artifact

Accepted

Which file owns content, and what may happen to an existing sibling HTML file?

Impact if wrong

Two editable sources create drift and can destroy hand-edited HTML. Preview-only output would fail the explicit requirement to create a companion file.

Proposed choice

Markdown is the only editable source. After a successful parse, generation replaces the same-named sibling .html file deterministically; the HTML is disposable and must never be read back as content.

Canonical Markdown Overwrite the derived companion only after the complete output is ready. Chosen in IDEA
Preview only Avoids generated files but does not satisfy the requested workflow.
Editable HTML companion Allows bespoke changes but creates a second source of truth.
Reasoning and review consequence

Why

This preserves the IDEA and the durable-source principle in the Crossroads manifesto. It intentionally updates PAT-001: canonical Markdown and shared assets remain, while manual template copying and the “no renderer runtime” clause are superseded for these two supported document types.

Review consequence

Review should treat generated HTML edits as non-durable and confirm repeat generation is byte-for-byte stable for unchanged Markdown.

C3

Markdown as the document grammar

Accepted

How does authored Markdown communicate document structure to the renderer?

Impact if wrong

Front matter, directives, or embedded HTML would permanently change how every issue and Planpoint is authored. Generic rendering would lose the semantic information needed by the exact layouts.

Proposed choice

Use the existing template headings as the schema and ordinary Markdown blocks—paragraphs, links, emphasis, inline code, fenced code, lists, task lists, and tables—as content. Add no renderer-specific tags, directives, or front matter.

Heading-defined schemas Keeps both files natural to read and edit while retaining document semantics. Chosen in IDEA
Metadata or directives Makes rendering explicit but pollutes the canonical Markdown format.
Generic CommonMark Needs no schema but cannot choose Framework components reliably.
Reasoning and review consequence

Why

The existing templates already contain stable semantic headings. They provide enough structure without creating a Crossroads-specific Markdown dialect.

Review consequence

Tests will use unchanged copies of both Markdown templates plus representative filled documents. Any template adjustment must remain valid, readable Markdown without hidden syntax.

C4

Local and safe rendering boundary

Accepted

May Markdown execute authored HTML or load network content inside the generated view?

Impact if wrong

Executing raw HTML or remote resources turns a local documentation preview into an active-content security boundary and makes output depend on network availability.

Proposed choice

Render offline from local workspace assets, escape raw HTML, validate links, and allow only the extension-owned tab and copy interactions. Do not fetch remote scripts, styles, fonts, or rendering services.

Safe local subset Predictable output with no authored script execution or runtime network dependency. Recommended
Trusted raw HTML Allows arbitrary embeds but expands the security surface and authoring language.
Remote renderer Centralizes rendering but sends local content out of the workspace and requires connectivity.
Reasoning and review consequence

Why

Crossroads documents are local by design, and the IDEA does not require raw HTML. The safe subset keeps generated files portable and the webview narrowly scoped.

Review consequence

Verification will include escaping hostile HTML, rejecting unsafe links, rendering without network access, and checking the webview content-security policy.

C5

Late-Crossroad policy

Accepted

What should happen if a new hard-to-reverse choice appears after the unattended build begins?

Impact if wrong

Stopping unnecessarily defeats the one-shot goal, while guessing at a high-cost choice can produce a product the user would need to unwind.

Proposed choice

Continue unattended with the option that has the lowest reversal cost, and record the late decision prominently in build.html.

Continue Delegates late Crossroads to the lowest-reversal-cost choice and preserves momentum. Recommended
Stop Leaves the repository safe and returns with the exact decision required.
Reasoning and review consequence

Why

This is a bounded, local project with no accounts, deployment, or external data, so most unforeseen choices should remain reversible.

Review consequence

Accepting Continue explicitly delegates unforeseen Crossroads; each one must still be visible in the final build record with its alternatives and rationale.

Proposed defaults

Hot decisions

Opinionated choices worth seeing before the build, but affordable to revise and delegated unless changed.

H1

Save, generate, and toggle behavior

Accepted

What exactly should Ctrl+Alt+Shift+V do across source and preview?

Proposed approach

From Markdown, save the active document, validate and generate its sibling HTML, then replace the active editor view with the preview in the same editor group. From that preview, the shortcut restores the Markdown editor in place. While open, each later Markdown save regenerates both file and preview; ordinary keystrokes never write HTML.

Why

The preview feels like VS Code’s Markdown viewer while every on-disk HTML file corresponds to saved Markdown. The official VS Code API supports contributed keybindings, commands, and fully controlled webviews for custom renderings.

Alternatives and review focus

Alternatives

Open source and preview side by side; render only when invoked; update the generated file on every keystroke; or open the HTML as plain text.

Review focus

Judge whether the in-place full-view toggle, automatic save, preserved editor-group position, and save-triggered refresh match the intended rhythm.

H2

Exact design and complete content

Accepted

How should known Markdown sections fit when the reference HTML does not show an explicit component for every section?

Proposed approach

Keep the existing DOM classes, dimensions, typography, colors, assets, tabs, and interaction language as the design contract. Render every known template section by repeating the nearest existing Framework component; omit an optional component only when its Markdown section is absent. Never add a generic unstyled Markdown fallback.

Why

This makes the HTML a complete view of the canonical file without inventing a second visual system. It applies STYLE-001 and keeps the current issue and Planpoint templates as golden references.

Alternatives and review focus

Alternatives

Render only the sections already visible in the example HTML and silently omit the rest; append a generic Markdown view for unmatched sections; or redesign the reference templates first.

Review focus

The behavioral prototype will make the issue and Planpoint mappings concrete. Confirm that repeated existing components preserve the exact intended hierarchy without hiding canonical content.

H3

Schema-aware validation

Accepted

Should malformed or newly structured Markdown produce partial output or fail before replacement?

Proposed approach

Parse CommonMark tokens with markdown-it, then validate them against the selected issue or Planpoint heading schema. Missing optional sections are valid; duplicate required sections, malformed decision blocks, and unknown top-level sections produce actionable VS Code diagnostics and leave the last valid HTML untouched.

Why

A real Markdown parser preserves ordinary formatting better than regular expressions, while schema validation prevents visually plausible but incorrect review documents.

Alternatives and review focus

Alternatives

Best-effort partial rendering; strict byte-for-byte adherence to the template; a hand-written regex parser; or dependence on VS Code’s non-public internal Markdown renderer.

Review focus

Check that valid variation is accepted, errors name the file and heading to fix, no failed render overwrites a valid companion, and the supported Markdown subset is documented.
